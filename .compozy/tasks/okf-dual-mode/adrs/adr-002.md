# ADR-002: promote is a mechanical non-LLM transform; type governance and a spec-compatible conformance posture

## Status

Accepted

## Date

2026-06-27

## Context

ADR-001 makes the research → operations distill loop the MVP's north star. That
loop has three behavioral questions the PRD must settle, each with product
consequences:

1. **What does `kb promote` do to the content?** It can be a mechanical
   format transform, or it can re-synthesize the content with an LLM.
2. **Where does the OKF `type` come from?** OKF requires exactly one field —
   `type` — and its value drives how consumers route, filter, and present a
   concept. Free-text typing risks drift (`Voice Profile` vs `voice-profile`).
3. **How strict is conformance, and what does `kb` emit?** Research surfaced two
   contradictions between the OKF spec and Google's own tooling:
   - The spec requires only `type`, but Google's reference producer requires
     `type` + `title` + `description` + `timestamp`, and all sample bundles carry
     them.
   - The spec *recommends* absolute `/path.md` links, but Google's tooling forbids
     them (they break GitHub rendering) and every sample bundle uses relative
     links.
   - The spec (§9) requires consumers to *tolerate* broken links, unknown types,
     and missing optional fields.

`kb`'s identity, per its own `CLAUDE.md`, is "the non-LLM workflow": scaffolding,
ingestion, structural linting. The user also explicitly values a consistent local
standard for concept types.

## Decision

**1. `promote` is a mechanical, non-destructive, non-LLM transform.**

`kb promote <wiki-doc> --to <okf-topic>` copies the source content into the OKF
bundle as a new typed concept and performs only structural work: convert
`[[wikilinks]]` to relative markdown links, remap wiki frontmatter to the OKF
contract, set the concept `type`, and append an entry to the bundle's `log.md`.
The source wiki document stays in `research/` (the immutable lab). No LLM is
invoked — any intelligent distillation/rewriting remains the job of the operator
or an external agent calling `kb`, exactly as the user's `second-brain/` was built.

**2. `type` is supplied explicitly and governed by a local vocabulary.**

`promote` (and native authoring) takes the concept kind via `--type`; a canonical
list of concept types lives in `kb.toml` (e.g. an `[okf].types` vocabulary). The
vocabulary exists to prevent duplication and enforce a per-vault standard. OKF
deliberately has no *global* type registry; a *local* vocabulary is fully
compatible and adds value. A type outside the vocabulary is a lint warning, not a
hard failure, and the vocabulary is extended by editing `kb.toml`.

**3. Conformance is compatible with the real-world tooling, lenient by default.**

- **Emit**: all four producer fields (`type`, `title`, `description`,
  `timestamp`) and **relative, GitHub-safe** markdown links.
- **Validate**: lenient per spec §9 — tolerate broken cross-links, unknown
  `type` values, and missing optional fields (so externally produced bundles are
  accepted in Phase 2).
- **Local standards as warnings** on the operator's own bundles: all four fields
  present, and `type` within the `kb.toml` vocabulary.
- **`--strict`** promotes warnings to errors for CI gates.

## Alternatives Considered

### Alternative 1: LLM-assisted `promote`

- **Description**: `promote` re-synthesizes the wiki document into a concise OKF
  concept via a configured provider.
- **Pros**: One-command "magic"; less manual rewriting.
- **Cons**: Injects an LLM dependency and nondeterminism into a tool whose
  identity is the non-LLM workflow; harder to test; unpredictable output.
- **Why rejected**: Contradicts `kb`'s stated identity; distillation already
  belongs to the operator/agent layer. (A future `--distill` flag is possible but
  out of scope.)

### Alternative 2: Derived or defaulted `type`

- **Description**: Infer `type` from the wiki document's `source_kind`/`domain`,
  or default everything to a generic `Reference`.
- **Pros**: Less typing.
- **Cons**: The wiki `type` is a stage marker (always `wiki`/`source`), so
  derivation carries no concept semantics; a generic default produces lazy
  bundles where every concept is `Reference`, defeating OKF's routing value.
- **Why rejected**: Kills the value of the one field OKF requires.

### Alternative 3: Spec-minimal or maximum-rigor conformance

- **Description**: Either emit/validate only `type` (spec-minimal), or make every
  rule a hard error by default (maximum rigor).
- **Pros**: Minimal is "pure"; maximum guarantees an iron standard.
- **Cons**: Minimal yields impoverished bundles misaligned with the official
  samples; maximum fights OKF's permissive philosophy and would reject
  third-party bundles during Phase 2 ingest.
- **Why rejected**: The tooling-compatible middle (emit four, validate lenient,
  warn locally, `--strict` opt-in) matches real bundles and the user's desire for
  a standard without sacrificing interoperability.

## Consequences

### Positive

- `promote` is deterministic, testable, and true to `kb`'s identity.
- Bundles align with Google's real samples and tooling, maximizing portability.
- The type vocabulary keeps the operator's catalog consistent over time.
- Lenient validation lets Phase 2 ingest accept real-world external bundles.

### Negative

- The operator (or an agent) still does the intelligent distillation; `promote`
  alone does not condense content.
- Two documented spec contradictions must be encoded as deliberate, documented
  deviations (emit four, emit relative links).

### Risks

- **Spec churn** (v0.1 draft) → keep emit/validate rules isolated and versioned.
- **Vocabulary friction** (warnings ignored) → `--strict` in CI keeps the
  standard enforceable when it matters.

## Implementation Notes

Detail belongs in the TechSpec. Product-level notes: `promote` appends to
`log.md` and the bundle's `index.md` is auto-maintained (OKF index files are
type-grouped bullet lists, which are mechanically generatable). Conformance rules
target OKF v0.1 and validate against the official sample bundles (GA4, Stack
Overflow, Bitcoin) as fixtures.

Two of the four producer fields have no source in `kb`-produced documents
(B-201): `description` comes from a `--description` flag, falling back to the first
body sentence and then to empty + warning; `timestamp` is the promote-time clock in
RFC3339 (promotion is the "last meaningful change"), since the only source dates are
date-only (`2006-01-02`). See the TechSpec remap table.
