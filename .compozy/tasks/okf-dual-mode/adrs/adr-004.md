# ADR-004: A `LinkFormatter` abstraction and full migration of the link call sites

## Status

Accepted

## Date

2026-06-27

## Context

Link emission is hardcoded to Obsidian `[[wikilinks]]`:

- `internal/vault/pathutils.go:244` `ToTopicWikiLink(topicSlug, documentPath,
  label)` → `[[slug/path|label]]`, with a thin wrapper `toSourceWikiLink(topic,
  relativePath, label)` at `render.go:186`.
- These are called from **~43 sites**, all in `internal/vault/render.go` and
  `render_wiki.go` — the **codebase→wiki** render pipeline.
- There is **no `Renderer`/`Writer` struct** in `internal/vault`; render functions
  receive `topic models.TopicMetadata` directly, so there is no constructor to
  inject a formatter into.

OKF requires standard markdown links instead of wikilinks (ADR-002: relative,
GitHub-safe). The question is how the link format becomes mode-aware, and how much
of the refactor lands in the MVP. The user chose to introduce the full abstraction
and migrate all call sites in the MVP, rather than defer the render-pipeline
refactor to Phase 3.

A key technical subtlety: an OKF **relative** link needs the **source document's
directory** to compute the path to the target. The current call sites pass only
the target path and a label.

## Decision

**1. Define a `LinkFormatter` interface in `internal/vault`** (rendering's home;
keeps the `okf`→`vault` dependency one-way and cycle-free):

```go
// LinkFormatter renders a link from the document being written (fromDir,
// bundle-relative) to a target document, with an optional label.
type LinkFormatter interface {
    Link(fromDir, targetPath, label string) string
}
```

- `WikiLinkFormatter` — ignores `fromDir`; emits `[[slug/target|label]]` exactly
  as `ToTopicWikiLink` does today (`ToTopicWikiLink` becomes its implementation).
- `OKFLinkFormatter` — emits a relative, GitHub-safe markdown link
  (`[label](relpath)`), computing `relpath` from `fromDir` to `targetPath`.

**2. Resolve the formatter from `topic.Mode`** via
`vault.LinkFormatterFor(topic) LinkFormatter`, and route every call site through a
single chokepoint helper `linkFor(topic, fromDir, targetPath, label)`. The direct
`ToTopicWikiLink(topic.Slug, …)` calls in `render_wiki.go` are converted to use this
helper too. (Verified call-site spread: ~7 sites in `render.go` plus ~34 matching
lines in `render_wiki.go`; treat "~43 sites" as the working estimate.)

**3. Scope the MVP correctly.** The 43 render sites belong to the codebase→wiki
pipeline, which produces **wiki-mode** topics; codebase→OKF is Phase 3. Therefore
in the MVP these sites continue to resolve `WikiLinkFormatter` (mode = wiki) and
emit byte-identical output. The **active** MVP consumer of `OKFLinkFormatter` is
`promote`'s body transform (which knows the concept's own directory) and
`index.md` generation. The OKF branch at the render sites is wired but dormant
until Phase 3.

## Alternatives Considered

### Alternative 1: Defer the render-site refactor; body-transform only in MVP

- **Description**: MVP does only `[[wikilink]]`→markdown in `promote` body text and
  index generation; the 43 sites are untouched until Phase 3.
- **Pros**: Smallest MVP; least risk.
- **Cons**: The abstraction lands later; two passes over the render code.
- **Why rejected**: The user chose to do the foundational abstraction now.

### Alternative 2: Add a `fromDir`/formatter argument to each call site signature

- **Description**: Thread source context explicitly through 43 signatures.
- **Pros**: Fully explicit.
- **Cons**: Churns 43 signatures for no MVP-exercised benefit.
- **Why rejected**: The chokepoint helper + `topic`-resolved formatter achieves the
  same with far less churn.

### Alternative 3: Package-global formatter strategy

- **Description**: A mutable package-level formatter set per run.
- **Pros**: No threading.
- **Cons**: Not concurrency-safe; hidden global state; hard to test.
- **Why rejected**: Violates testability.

## Consequences

### Positive

- One mode-aware seam for all link emission; Phase 3 only flips render topics to
  OKF mode and supplies `fromDir`.
- `promote` and index generation reuse the same formatter.

### Negative

- A large mechanical refactor whose OKF branch is not exercised at render sites in
  the MVP.

### Risks

- **Silent regression** in wiki output during the refactor → mitigate with golden
  tests asserting byte-identical wiki render output before/after, and keep the
  existing `vault` test suite green.
- **Relative-path edge cases** (siblings, parents, root) in `OKFLinkFormatter` →
  cover with table-driven unit tests including `fromDir == targetDir` and nested
  cases.
- **Dormant OKF render branch ships as dead code in the MVP** (N-001) → add one
  render-site-in-`okf`-mode smoke test so the wired branch and its `fromDir`
  plumbing are exercised, keeping the user's "migrate now" decision without shipping
  untested code.

## Implementation Notes

`OKFLinkFormatter.Link` uses `filepath.Rel(fromDir, targetPath)` semantics on
forward-slash bundle paths, never emitting a leading `/` (GitHub-safe, per
ADR-002). `WikiLinkFormatter` preserves `StripMarkdownExtension` behavior. The
formatter is selected once per document render from `topic.Mode`.
