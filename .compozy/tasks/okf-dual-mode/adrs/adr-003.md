# ADR-003: A cohesive `internal/okf` package and a `mode` field on the topic model

## Status

Accepted

## Date

2026-06-27

## Context

OKF dual-mode (ADR-001) introduces a substantial new concern: an OKF frontmatter
contract, a wikilink→markdown transform, `index.md`/`log.md` generation, a
conformance checker, and the `promote` orchestration. The existing packages own
the LLM-Wiki pyramid:

- `internal/topic` — scaffold + `topic.yaml` (`topicMetadataFile` at
  `topic.go:104`; scaffold list `currentTopicDirectories` at `topic.go:38`).
- `internal/vault` — render/read/write of documents.
- `internal/lint` — path-prefix structural validation (`schemaForPath`).
- `internal/ingest` — frontmatter assembly (`buildFrontmatter` at `ingest.go:160`).

Two structural needs must be settled before any behavior is built: where OKF logic
lives, and how a topic signals it is an OKF bundle versus a wiki.

## Decision

**1. A new cohesive `internal/okf` package owns all OKF behavior.**

It contains: the OKF frontmatter contract (the four producer fields), the
`[[wikilink]]`→relative-markdown transform, `index.md`/`log.md` generation, the
conformance checker (ADR-005), and the `promote` orchestration. Dependency
direction is one-way: `internal/okf` imports `internal/frontmatter`,
`internal/vault` (document read/write), `internal/config` (the type vocabulary),
and `internal/models`; none of those import `internal/okf`. This prevents import
cycles and keeps the wiki packages free of OKF concerns.

**2. Add a `mode` field to the topic model, defaulting to wiki.**

- `internal/models`: typed constants `TopicModeWiki = "wiki"` and
  `TopicModeOKF = "okf"`, and a `Mode` field on `models.TopicMetadata`
  (`models.go:271`) and `models.TopicInfo`.
- `internal/topic`: `Mode string \`yaml:"mode,omitempty"\`` on `topicMetadataFile`
  (`topic.go:104`); written by `writeMetadataFile` and read by
  `readTopicYAMLMetadata` (`topic.go:770`).
- An absent/empty `mode` is normalized to `wiki` on read, so existing topics and
  existing `topic.yaml` files behave identically (zero regression).

## Alternatives Considered

### Alternative 1: Spread OKF logic across existing packages

- **Description**: `mode` in topic, links in vault, conformance extending lint,
  `promote` in ingest.
- **Pros**: Maximum reuse; no new package.
- **Cons**: Dilutes OKF across four packages; entangles it with the wiki pyramid;
  harder to test and to grow in Phase 2/3.
- **Why rejected**: Cohesion and a clean phase-growth boundary outweigh avoiding a
  new package.

### Alternative 2: Hybrid (okf package + okf logic also in vault/topic)

- **Description**: Core in `internal/okf`, but the link formatter and `mode`
  scattered into vault/topic.
- **Pros**: Avoids some indirection.
- **Cons**: The boundary becomes ambiguous (OKF logic in two homes).
- **Why rejected**: Only the genuinely cross-cutting `LinkFormatter` belongs in
  vault (ADR-004); everything else stays in `internal/okf`. The `mode` field is a
  data-model fact, not OKF logic, so it correctly lives on the topic model.

## Consequences

### Positive

- One obvious home for OKF; isolated unit/integration testing.
- Clean dependency graph; Phase 2/3 (export/ingest/codebase→OKF) extend one package.
- `mode` is a tiny, backward-compatible addition.

### Negative

- A new package and a field threaded through topic load/write.

### Risks

- **Mode drift** (a topic with an unknown mode) → normalize unknown/empty to
  `wiki` and reject unknown explicit values at scaffold time.

## Implementation Notes

`topicMetadataFile` marshals via `yaml.Marshal`. The zero-regression story has two
distinct parts (N-004): (a) **existing** `topic.yaml` files are never rewritten and
read-normalize empty `mode`→`wiki`, so they are byte-stable; (b) **new** scaffolds
write an explicit `mode` value, so a freshly created wiki topic's `topic.yaml` will
contain a visible `mode: wiki` line — a scaffold-output change (update the scaffold
golden expectation accordingly), not a change to old files. `omitempty` only
suppresses a programmatically-empty mode. Topic resolution (`topic.Resolve`/`Info`)
must surface `Mode` so downstream commands (`promote`, `okf check`) can branch.
