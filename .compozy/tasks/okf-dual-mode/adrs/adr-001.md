# ADR-001: OKF as a first-class authoring mode, not an export-only projection

## Status

Accepted

## Date

2026-06-27

## Context

The `kb` CLI implements the Karpathy "LLM-wiki" pattern: a research lab where raw
sources are ingested, compiled into a wiki, queried, and linted. Google Cloud
released the Open Knowledge Format (OKF) v0.1 (2026-06-12), which formalizes the
same markdown+YAML-frontmatter substrate but optimizes for a different purpose: a
portable, vendor-neutral **catalog/interchange** artifact that other people's
agents consume.

These are two distinct knowledge lifecycles on the same substrate:

- **LLM-Wiki** = a *lab* (ingest → compile → query → lint; `[[wikilinks]]`;
  `raw/` + `wiki/`; stage markers; for the operator to explore).
- **OKF** = a *catalog/API* (declare → consume; required `type` per concept;
  markdown links; flat typed concepts; for others to consume; portable).

This mirrors the duality the user already maintains by hand in their workspace:
`research/` (LLM-wiki) where they research, and `second-brain/` (OKF) where they
declare "what is mine" for operations.

An earlier internal proposal treated OKF as an **export-only projection** of the
wiki. The user found this too thin: it captures only the "publish" direction and
ignores the daily, high-leverage flow of distilling research into the operational
catalog. The question is whether OKF is a derived output of the wiki or a
first-class mode in its own right.

## Decision

Make OKF a **first-class authoring mode** of `kb`, selectable per topic, with
the LLM-Wiki mode remaining the default.

- Introduce a per-topic **`mode: wiki | okf`** (default `wiki`).
- An **OKF bundle is modeled as a `kb` topic with `mode: okf`** — it reuses the
  existing topic, vault, lint, and index machinery rather than becoming a parallel
  standalone concept. `mode` disambiguates scaffold shape, link format, frontmatter
  contract, and lint ruleset.
- The MVP optimizes the **research → operations distill loop**: native OKF
  authoring plus a `promote` interop verb (see ADR-002), not export.
- Deliver in phases:
  - **MVP (Phase 1):** `mode` field, OKF scaffold (`kb topic new --mode okf`),
    `kb promote` (wiki → OKF), `kb okf check` (conformance).
  - **Phase 2:** `kb export okf` (publish a wiki topic as a portable bundle) and
    `kb ingest okf` (consume an external bundle into research).
  - **Phase 3:** codebase → OKF (the typed symbol/relation graph emitted as a
    bundle) — the standout differentiator demo.

## Alternatives Considered

### Alternative 1: Export-only projection (OKF as a derived output)

- **Description**: Add `kb export okf` that renders an existing wiki topic into an
  OKF bundle; no OKF authoring, no `mode`, no interop loop.
- **Pros**: Smallest surface; no scaffold or link-format refactor; quick to ship.
- **Cons**: Captures only "publish"; cannot author or maintain operational
  bundles; ignores the daily research→org distill the user lives; treats OKF as
  second-class.
- **Why rejected**: Too thin; misses the highest-leverage use case.

### Alternative 2: Standalone OKF concept (separate from topics)

- **Description**: A new `kb okf init`/`kb okf …` surface independent of topics,
  with its own metadata and storage.
- **Pros**: Clean conceptual separation between lab and catalog.
- **Cons**: Duplicates topic, vault, lint, and index machinery; two parallel
  models to maintain; more user-facing surface to learn.
- **Why rejected**: `mode` on the existing topic achieves the same separation with
  far less duplication and a smaller learning curve.

### Alternative 3: Single unified model (one mode, derive both views)

- **Description**: Keep one internal model and render either wiki or OKF on demand.
- **Pros**: No mode flag.
- **Cons**: The two lifecycles diverge on link format, frontmatter contract, and
  conformance; forcing one model creates leaky, ambiguous behavior (e.g., the
  `type` field means "stage" in wiki and "concept kind" in OKF).
- **Why rejected**: `mode` cleanly disambiguates the conflicts instead of hiding
  them.

## Consequences

### Positive

- The user's existing `research/` vs `second-brain/` split becomes
  tool-enforced rather than maintained by hand.
- Default `mode: wiki` means zero regression for existing topics.
- Reusing the topic model keeps the new surface small and learnable.
- Phasing keeps an already-large MVP focused on the daily loop.

### Negative

- The MVP is larger than an export-only effort (mode + scaffold + two new verbs).
- A shared link-emission path must support both wikilinks and OKF markdown links.

### Risks

- **OKF is a v0.1 draft** → pin conformance to v0.1 and isolate the ruleset so it
  can evolve without touching the rest of the tool.
- **Scope creep** (the MVP touches several surfaces) → strict phasing; export,
  ingest, and codebase→OKF are explicit non-goals for the MVP.

## Implementation Notes

Implementation detail belongs in the TechSpec. At a product level: the link
emission path is currently wiki-only and must become mode-aware; the topic
scaffold and lint ruleset must branch on `mode`. No existing behavior changes when
`mode` is absent or `wiki`.
